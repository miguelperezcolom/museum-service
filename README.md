# museum-service — several art museums behind one writable API

A demo backend for [Mateu](https://github.com/miguelperezcolom/mateu): **real public-domain artworks**
from three museums, with search, filters, ranges, paging, writes and real references between tables,
over an in-memory H2 seeded at boot. It replaces the Star Wars data of
[swapi-service](https://github.com/miguelperezcolom/swapi-service) (whose pictures carry no free
licence) and follows the same conventions — same query grammar, same envelope, same write key.

**Contract:** [`/swagger-ui.html`](http://localhost:8121/swagger-ui.html) · [`/v3/api-docs`](http://localhost:8121/v3/api-docs)

## Where the data comes from — and why it may be shown

| Museum | Open-access API | What is kept | Licence |
|---|---|---|---|
| The Metropolitan Museum of Art | `collectionapi.metmuseum.org` | objects with `isPublicDomain: true` and an image | [CC0](https://www.metmuseum.org/hubs/open-access) — data and images |
| Statens Museum for Kunst (SMK, Copenhagen) | `api.smk.dk` (images through its IIIF server, `iip.smk.dk`) | `public_domain: true` with an image | [SMK Open](https://open.smk.dk): images of public-domain works under the [Public Domain Mark](https://creativecommons.org/publicdomain/mark/1.0/), metadata CC0 |
| Cleveland Museum of Art | `openaccess-api.clevelandart.org` | `share_license_status: CC0` with an image | [CC0](https://www.clevelandart.org/open-access) — data and images |

- The records were fetched **once** by [`scripts/build-seed.py`](scripts/build-seed.py) and committed
  as JSON in [`src/main/resources/seed/`](src/main/resources/seed). **The service never calls a
  museum at run time.**
- **The images are not copied.** Every artwork links the museum's own official image URLs — the
  museums publish them for exactly this use: a small one (`imageSmall`) for lists and cards and a large
  one (`imageLarge`) for a detail page — and a link to the work's page on the museum's site
  (`sourceUrl`).
- Neither licence asks for anything, but the museums ask for a courtesy credit, so every artwork carries
  `imageCredit` (`"The Metropolitan Museum of Art · CC0"`, `"Statens Museum for Kunst · Public domain"`), [`/api/credits`](http://localhost:8121/api/credits)
  lists them all, and [`CREDITS.md`](CREDITS.md) is the same list on paper.
- **Why not the Art Institute of Chicago?** It was the first choice — its data is CC0 — but its
  IIIF image server sits behind a Cloudflare challenge that refuses image requests from other sites,
  even from a real browser, so its pictures cannot be linked from a demo page. SMK's can.
- The museums' names say where a work is held. This project is not affiliated with or endorsed by any
  of them.

### What is synthetic

Museums do not publish valuations, loan agreements or conservation schedules, and a UI needs
something to plan, track and chart. So these are **generated by the seed script — plausible and
deterministic** (every draw comes from a hash of the record it is about, or from a seeded generator
over records in a fixed order; running the script twice over the same cache writes the same files):

- each artwork's `estimatedValue` (USD, log-uniform within a band per kind of object);
- the exhibitions (6 per museum: 2 closed, 2 open, 2 planned, around 31 Oct 2026), their curators,
  budgets and visitor counts;
- the loans between museums, spread over the whole workflow;
- the conservation tasks (a board per museum);
- the daily visits (1 Jan → 31 Oct 2026, open days only — the Met closes on Wednesdays, SMK and
  Cleveland on Mondays; Cleveland is free);
- every person's name, and the artists' one-line bios (built from the records, not copied);
- each artist's `image`, which is **a work by the artist, not a portrait** (CC0 portraits are rare),
  and says so in its credit.

## The data model

```
Museum ──1:N── Department ──1:N── Artwork ──N:1── Artist
   │                                 │  │
   ├──1:N── Exhibition ──M:N─────────┘  ├──1:N── Loan ──N:1── Museum (from, to), Exhibition
   └──1:N── Visit                        └──1:N── ConservationTask
```

| collection | rows | owns |
|---|---|---|
| `/api/museums` | 3 | — |
| `/api/departments` | 33 | `museum` |
| `/api/artists` | 200 | — |
| `/api/artworks` | 399 (Met 132, SMK 122, Cleveland 145) | `artist`, `museum`, `department` |
| `/api/exhibitions` | 18 | `museum`, `artworks` (M:N) |
| `/api/loans` | 53 | `artwork`, `fromMuseum`, `toMuseum`, `exhibition` |
| `/api/conservation-tasks` | 72 | `artwork` |
| `/api/visits` | 783 | `museum` |

Plus two read-only aggregates:

- `GET /api/stats` — the numbers a dashboard opens with (totals, per museum, by status, visitors by
  month), computed from the live tables, with the big numbers also pre-formatted (`visitorsYtdLabel`:
  `"5.72 M"`) because a UI template interpolates; it does not format.
- `GET /api/collection-tree` — museum → department → gallery, as rows with `children`, in the same
  `{content, totalElements}` envelope, for a tree view.

**Artists are shared across museums**: Rodin is one row with works in New York and Cleveland, so
"by artist" is a real join. `classification` is folded into one short vocabulary (Painting,
Sculpture, Photograph, Arms and Armor…) so it filters as a pick; the museum's own term stays in
`objectType`.

Status vocabularies, as stored:

| field | values |
|---|---|
| `exhibitions.status` | `planned` · `open` · `closed` |
| `loans.status` | `requested` → `approved` → `in_transit` → `on_display` → `returned` |
| `conservation-tasks.status` | `backlog` · `in_progress` · `review` · `done` |
| `conservation-tasks.priority` | `low` · `medium` · `high` · `urgent` |

**Board order.** Each conservation task carries `boardOrder`, a decimal giving its place in its board
column (ascending). The seed numbers every column by due date, 1000 apart; a board move writes the
midpoint of the card's new neighbours (e.g. `1500.5`), so nothing is renumbered. `GET
/api/conservation-tasks?sort=boardOrder` returns a column in board order. A write that sends no
`boardOrder` (an edit form) keeps the card where it is; a new card goes to the end of its column.
This is what Mateu's Kanban `orderField` reads and writes.

## Reading

```bash
GET /api/artworks?search=monet                          # free text over the collection's text fields
GET /api/artworks?classification=Painting               # a declared filter (an exact pick)
GET /api/artworks?classification=Painting,Photograph    # comma-joined (or repeated) = OR — a multi-select
GET /api/artworks?onView=true                           # a boolean filter
GET /api/artworks?estimatedValue_from=1000000&estimatedValue_to=5000000   # inclusive range
GET /api/artworks?museumId=1&departmentId=3             # by reference
GET /api/artworks?exhibitionId=4                        # through a many-to-many: the works a show hangs
GET /api/exhibitions?startDate_from=2026-01-01&sort=startDate,desc
GET /api/conservation-tasks?museumId=2&status=review    # a reference reached through another one
GET /api/artworks?sort=museumName&page=2&size=50        # sort by the name a row shows
```

Every condition is evaluated **by the database**. The response is an envelope:

```json
{ "content": [ … ], "totalElements": 399, "totalPages": 20, "page": 0, "size": 20 }
```

A **filter the collection does not declare is a 400**, never a silently unfiltered page; so is an
unknown sort key and an unparseable value. References come back as ids plus the display name for the
single-valued ones:

```json
{ "id": 133, "title": "Wood with Crooked Tree", "artistId": 66, "artistName": "Mogens Ballin",
  "museumId": 2, "museumName": "Statens Museum for Kunst", "classification": "Painting",
  "estimatedValue": 20000000.0, "onView": true, "gallery": "Room 225",
  "imageSmall": "https://iip.smk.dk/iiif/jp2/gf06g715p_kms8914.tif.jp2/full/!400,/0/default.jpg",
  "imageLarge": "https://iip.smk.dk/iiif/jp2/gf06g715p_kms8914.tif.jp2/full/!1200,/0/default.jpg",
  "imageCredit": "Statens Museum for Kunst · Public domain",
  "sourceUrl": "https://open.smk.dk/artwork/image/KMS8914", "url": "/api/artworks/133" }
```

## Writing

Reads are open. **Writes need the `X-Api-Key` header** — not authentication, but the difference
between "you have to be told about it" and "a crawler can empty the database".

```bash
curl -X POST http://localhost:8121/api/loans \
  -H 'Content-Type: application/json' -H 'X-Api-Key: localdev' \
  -d '{"artworkId":1,"exhibitionId":9,"startDate":"2027-03-01","endDate":"2027-06-30","insuranceValue":12000000}'
```

`POST` → 201 with a `Location`; `PUT /{id}` replaces; `DELETE /{id}` → 204. Conveniences a form
appreciates:

- values may arrive as strings (`"artworkId":"1"`) and blanks as empty strings — what a form sends;
- a new loan leaves from the artwork's own museum and goes to the exhibition's museum unless the body
  says otherwise, and starts as `requested`; a new task starts in `backlog`;
- a `PUT` never blanks an artwork's (or museum's, or artist's) **image, credit or source link**: left
  out or blank, the stored value stays — those are the museum's, not the editor's.

A write pointing at a row that does not exist is a **400**; deleting a row others still reference
(an artwork on a loan) is a **409**, and nothing is lost; a create beyond the row ceiling
(`museum.max-rows-per-collection`, 3000) is a **507**. **The database is in memory and re-seeded on
every restart**, so anything written here is demo data with a short life.

### A loan's documents

A loan carries files — its agreement, condition reports, receipts:

```bash
# upload: the file as a base64 data URI (what a browser's FileReader produces); `name` is optional —
# without it the URI's `name=` parameter is used (`data:application/pdf;name=agreement.pdf;base64,…`)
curl -X POST http://localhost:8121/api/loans/1/documents \
  -H 'Content-Type: application/json' -H 'X-Api-Key: localdev' \
  -d "{\"name\":\"agreement.pdf\",\"content\":\"data:application/pdf;base64,$(base64 < agreement.pdf | tr -d '\n')\"}"
curl http://localhost:8121/api/loans/1/documents          # {content:[{id,name,contentType,size,uploadedAt,url}], totalElements}
curl -O -J http://localhost:8121/api/loans/1/documents/1  # the bytes, with their type and name
curl -X DELETE -H 'X-Api-Key: localdev' http://localhost:8121/api/loans/1/documents/1
curl -X DELETE -H 'X-Api-Key: localdev' http://localhost:8121/api/loan-documents/2   # by its id alone
```

Kept: PDF, PNG/JPEG/GIF/WebP, plain text and CSV, Word/Excel/PowerPoint and OpenDocument — never
HTML, SVG or anything a browser would run, since the bytes are served from this origin. At most 5 MB
each and `museum.max-documents-per-loan` (20) per loan; anything else is a **400** that says why. Each
`url` is absolute, so a UI can open it in a new tab. Deleting a loan deletes its documents.

## Running it

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)
mvn spring-boot:run -Dspring-boot.run.arguments=--museum.write-key=localdev
# → http://localhost:8121/swagger-ui.html
```

Without a write key configured **every write is refused with 401**.

```bash
mvn verify      # 20 integration tests (MockMvc) over the real seeded dataset
```

CORS is open (`*`) for reads and writes, so a page in a browser can call the API directly.

## Rebuilding the seed

```bash
python3 scripts/build-seed.py            # fetches what is not cached yet (scripts/.cache, git-ignored)
python3 scripts/build-seed.py --offline  # rebuilds from the cache alone
```

The script picks, per museum, a fixed quota of works per department (paintings, sculpture, arms and
armour, photography, Asian, Egyptian, Greek and Roman, decorative arts, textiles…) for variety,
preferring each museum's own highlights, and keeps only public-domain/CC0 records with an image. The
museums' collections change over time, so a fresh fetch may pick other works; the tests pin the
committed seed's numbers.
